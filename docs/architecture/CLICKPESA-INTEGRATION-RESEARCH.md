# ClickPesa Integration Research

**Research date:** 2026-08-15

## Verified official behavior

ClickPesa provides API, hosted, and embedded integration options. Its collection products include USSD Push, card payments, BillPay, TanQR/Lipa Namba, and CRDB Direct Debit. For VetKonnect badge subscriptions, USSD Push is the relevant first payment flow; recurring subscription renewal must not be assumed to be supported by USSD Push and should be implemented as an application renewal workflow unless ClickPesa confirms a recurring mandate product for the merchant account.

The official API uses a token generated by `POST https://api.clickpesa.com/third-parties/generate-token` with `client-id` and `api-key` headers. The returned JWT is documented as valid for one hour and already includes the Bearer prefix for subsequent requests.

USSD Push uses a preview request at `POST /payments/preview-ussd-push-request`, followed by an initiation endpoint documented in the USSD-PUSH API section, and payment-status querying by order reference. Preview fields include `amount`, `currency` (`TZS`), `orderReference`, `phoneNumber` with country code and no plus sign, and optional `fetchSenderDetails`. Order references must be unique and alphanumeric.

ClickPesa documents application-level webhooks for application-linked collection transactions, including USSD Push. Relevant events for this integration are `PAYMENT RECEIVED` and `PAYMENT FAILED`. A successful payment payload includes event, status, paymentReference, orderReference, collectedAmount, collectedCurrency, channel, timestamps, and customer data. The receiver must return a 2xx response to acknowledge receipt.

ClickPesa documents checksum protection for API payloads and webhooks. The checksum is an HMAC-SHA256 over compact JSON of recursively alphabetized object keys, excluding `checksum` and `checksumMethod`. The checksum key is configured in ClickPesa developer settings. Credentials, checksum keys, and raw provider secrets must remain environment-managed and must never be stored in payment records or returned by APIs.

## Implementation decisions

The backend will treat KYC verification and subscription payment as separate gates. A veterinarian may have a verified professional profile but receives the public badge only when an active, fully paid badge subscription exists. Payment state changes will be driven by verified webhooks and idempotent reconciliation, not by client claims or redirect success. Subscription renewal will be represented explicitly and will not silently auto-charge a user unless the ClickPesa merchant account and product contract support recurring mandates.
